## 1. 我对项目的理解

**一句话**：一个跑在本机的绿色软件，C 写的后端负责所有真实的网络 / 串口通信，浏览器作为统一操作界面，把 HTTP、FTP、TFTP、SMB、Telnet、SSH、串口（以及原始 TCP/UDP）的调试集中在一个窗口里。

**推测的典型场景**（请纠正）：

1. 嵌入式 / 网络设备联调：设备作为 FTP / TFTP / HTTP 客户端上传日志、拉取固件，工具作为**服务端**接住并显示。
2. 设备管理面调试：telnet / ssh 登录设备 CLI；串口接 console 口看启动日志。
3. 文件服务验证：SMB 共享浏览 / 读写，验证权限与路径。
4. 接口联调：构造任意 HTTP 请求，观察原始报文、耗时、响应。
5. 现场 / 产线：串口指令收发、定时心跳、十六进制裸数据调试。

**关键判断**：这更像「多协议调试工作台」，而不是「协议教学 demo」。因此会话管理、原始报文可见、日志、十六进制视图、断线重连这些"外围"能力，权重不低于协议本身。

## 2. 三个硬约束（直接决定架构）

1. **浏览器不能直接建 TCP/UDP 连接，也不能读写串口。** 所有协议必须在 C 后端实现，前端只负责发指令、渲染结果。
2. **浏览器发 HTTP 受同源策略限制**（不能随意设置 Host、Cookie、受限头，跨域需要目标站 CORS）。所以 HTTP 调试必须由后端代理发出，不能用 `fetch` 直连目标。
3. **前端不适合持有长连接状态和大文件。** 文件传输、终端流、串口流统一走「后端 + WebSocket」，前端只做流式展示。

## 3. 总体架构（建议）

```
┌───────────────────────────── 浏览器（单页前端） ─────────────────────────────┐
│  会话树 │ 多标签工作区 │ 终端(xterm.js) │ HEX 视图 │ 文件双栏 │ 日志/状态栏  │
└───────────────────────────────┬──────────────────────────────────────────────┘
                    HTTP(REST)  │  WebSocket(双向流)
┌───────────────────────────────▼──────────────────────────────────────────────┐
│ L5 API 层        HTTP/1.1 服务 + REST + WS + 内嵌静态资源（前端编译进 exe）   │
├──────────────────────────────────────────────────────────────────────────────┤
│ L4 会话层        会话注册/生命周期、环形缓冲、背压、事件总线、日志落盘        │
├──────────────────────────────────────────────────────────────────────────────┤
│ L3 协议层        http │ ftp │ tftp │ smb │ telnet │ ssh │ serial │ raw tcp/udp│
├──────────────────────────────────────────────────────────────────────────────┤
│ L2 传输层        TCP client/server、UDP、TLS、串口（OVERLAPPED / 读线程）     │
├──────────────────────────────────────────────────────────────────────────────┤
│ L1 平台层        socket / 串口 / 文件 / 编码 / 系统错误码（Win32 优先，POSIX 可移植）│
└──────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 并发模型

- HTTP 服务：少量线程（或单线程 + 短任务队列）。
- 每个协议会话：**独立线程 + 阻塞 socket + 环形缓冲**。
- WS 推送：每会话一个发送队列，限制上限，超限时暂停读或丢帧并告警。

理由：调试工具并发量小（几个到几十），线程模型代码直白、易调试、不易出现状态机 bug。事件循环（libuv）吞吐更好，但把每个协议写成状态机的复杂度不划算，不建议首版采用。

### 3.2 技术选型

| 用途 | 候选 | 许可 | 结论 / 说明 |
|---|---|---|---|
| HTTP + WS 服务 | civetweb | MIT | 可嵌入、自带 WS，首选 |
| | 自写 | — | 可控，但要写 WS 握手/帧/分片，约 800 行 |
| | mongoose | GPL-2.0 / 商业 | 许可风险，不用 |
| TLS | OpenSSL 3 / mbedTLS | Apache-2.0 | 静态链接 mbedTLS 更省事，OpenSSL 兼容性更好 |

## 4. 功能需求

### 4.0 通用能力（所有协议共享）

| 分类 | 需求 |
|---|---|
| 会话 | 新建 / 命名 / 分组 / 克隆 / 保存 / 导入导出(JSON) / 最近使用 / 多标签 |
| 连接 | 超时、重试、断线自动重连（可配间隔/次数）、连接中可取消 |
| 视图 | 文本 / HEX（偏移 + ASCII）/ 原始报文 / 时间戳（绝对·相对）/ 收发分色 / 暂停自动滚动 / 搜索过滤 / 清空 / 导出 |
| 发送 | 文本 / HEX / 文件；行尾（\r\n、\n、\r、无）；编码（UTF-8/GBK/ASCII）；定时发送（周期 + 次数）；快捷指令列表；循环测试 |
| 日志 | 按会话落盘、滚动上限、时间戳、导出 txt/bin |
| 状态 | 连接状态、收发字节/速率、错误原因（系统错误码 + 可读文本） |
| 安全 | 密码不明文存储（DPAPI 或本地密钥加密）、日志脱敏开关 |
| 全局 | 中英文、深/浅主题、快捷键、单实例、托盘退出 |

### 4.1 串口 ⚠

- **必做**：枚举（含 USB VID/PID 与友好名）；5–8 数据位、校验、停止位、流控（无/RTS-CTS/XON-XOFF）；任意波特率；DTR/RTS 手动控制；文本 + HEX 双视图；定时发送；快捷指令；日志。
- **应做**：多串口并发；自动重连（USB 拔插）；文件发送（分块 + 进度）；编码切换；高波特率不丢数据（≥921600）。
- **可后做**：RS-485 方向控制（RTS 翻转/延时）；数据统计（帧数/错误）。
- **首版不做**：虚拟串口对驱动。
- **验收**：921600 连续灌数据 10 分钟字节数一致；拔插后 5s 内自动恢复。

### 4.2 Telnet ⚠

- **必做**：连接/登录（账号密码提示）；IAC 协商（ECHO/SGA/NAWS/TTYPE/BINARY）；终端类型与窗口大小；VT100/ANSI 渲染（xterm.js）；本地/远端回显处理；CR/LF 规范化；编码；断线重连。
- **应做**：原始字节模式（绕过协商，纯 TCP 透传）；定时发送；宏/快捷键；多会话。
- **可后做**：LINEMODE；**服务端模拟**（让设备 telnet 进来，返回脚本化 CLI）；手工构造选项协商。
- **不做**：IBM 3270 等专用终端仿真。
- **验收**：登录 Cisco/H3C 风格 CLI 正常；方向键/Tab/退格可用；中文不乱码。

### 4.3 SSH ⚠

- **必做**：密码登录；公钥登录（RSA/ECDSA/Ed25519，支持 passphrase）；keyboard-interactive；known_hosts（首次信任/严格/忽略）；shell + PTY + 窗口 resize；exec 单命令；保活；编码。
- **应做**：SFTP 浏览/上传/下载（与 FTP/SMB 共用文件面板）；**算法兼容模式**（ssh-rsa、dh-group1-sha1、aes-cbc 等老设备）；跳板机（ProxyJump）。
- **可后做**：本地/远程/动态端口转发；SSH 服务端模拟。
- **不做**：证书签名登录（首版）。
- **风险**：OpenSSH 8.8+ 默认禁用 SHA-1 算法，老设备联调必须能显式开启——这是刚需，不是可选项。
- **验收**：分别连通 OpenSSH 9.x 与老式设备；断网 30s 内可重连；SFTP 传 1GB 文件内存平稳。

### 4.4 HTTP ⚠

- **必做（客户端）**：方法/URL/查询参数/Header 表格/Body（无、form、JSON、文本、二进制文件）；Basic/Bearer 认证；超时；重定向开关；代理；TLS 校验开关 + 自签证书；原始请求报文预览与编辑；响应状态/头/体；耗时（TTFB/总）；大小；格式化（JSON/XML/HTML）/HEX/预览；gzip/deflate 解压；chunked 显示；Cookie 管理；历史记录；环境变量（`{{base_url}}`）；集合/文件夹。
- **应做**：multipart 文件上传；响应保存到文件；断言（状态码/JSONPath/包含）；批量运行；cURL 导入。
- **可后做**：HTTP/2（nghttp2）；WebSocket 客户端调试；SSE；**服务端 Mock**（自定义路由返回固定响应，用于设备回调测试）。
- **不做**：页面渲染 / JS 执行。
- **验收**：覆盖 Postman 常见请求；原始报文与 tcpdump 一致；自签 HTTPS 可通。

### 4.5 FTP ⚠

- **必做（客户端）**：登录（匿名/账号）；主动（PORT/EPRT）与被动（PASV/EPSV）；目录（LIST/NLST/MLSD）；上传/下载/续传（REST）/删除/重命名/建目录；ASCII/BINARY；进度/速率/剩余时间；取消；目录树；拖拽；编码（GBK/UTF-8、OPTS UTF8）；超时与 NOOP 保活。
- **应做**：FTPS（AUTH TLS，显式/隐式）；递归上传下载；FEAT 能力协商；**原始命令控制台**（手发命令看响应）。
- **可后做**：FTP **服务端模拟**（设备作客户端上传/下载场景）；限速。
- **不做**：SFTP（归入 SSH）、SCP。
- **验收**：中文文件名不乱码；1GB 文件续传成功；NAT 后被动模式可用。

### 4.6 TFTP ⚠

- **必做（客户端 + 服务端）**：RRQ/WRQ；DATA/ACK/ERROR/OACK；重传与超时；`blksize`/`tsize`/`timeout` 选项（RFC 2347–2349）；TID 端口正确性；进度。
- **应做**：`windowsize`（RFC 7440）；服务端指定根目录 + 只读/读写；并发多客户端；逐块日志。
- **可后做**：组播 TFTP；选项协商可视化。
- **验收**：与 busybox tftp、Windows TFTP 客户端互通；100MB 固件传输 MD5 一致；5% 丢包下仍能完成。

### 4.7 SMB ⚠

- **必做（建议仅客户端）**：SMB2/2.1/3.0–3.1.1 协商；NTLMv2 认证（域/本地账号）；共享枚举；目录浏览；上传/下载/删除/重命名/建目录；大文件流式；进度；签名。
- **可后做**：SMB1（老设备，需另选库或自写，成本高）；SMB3 加密；DFS；SMB **服务端模拟**（成本极高，强烈不建议）。
- **风险**：自研 SMB 不现实，必须用库；libsmb2 为 LGPL-2.1，静态链接进闭源 exe 有合规成本 → 改为 DLL 动态链接，或接受 LGPL。
- **验收**：连通 Windows Server / Samba / 群晖各一台；100GB 文件读写不漏；中文与特殊字符路径正常。

### 4.8 建议补充的基础协议（强烈建议纳入首版）

**原始 TCP 客户端/服务端、UDP 客户端/服务端 + HEX 收发。** 这是所有协议的底座，也是排障最常用的能力，实现成本约等于"串口逻辑换个 I/O 层"。可选再加：DNS 查询、TCPing、NTP/时间。

### 4.9 明确不做（首版）

- 抓包（PCAP）与协议深度解析 —— 与 Wireshark 互补，本工具只保证可导出原始字节。
- 脚本引擎 / 自动化测试平台（后续可加简单断言）。
- 多用户与权限体系。
- 移动端适配。

## 7. 前后端接口草案

```
POST   /api/sessions                 {type, config} -> {id}
GET    /api/sessions                 -> 会话列表与状态
DELETE /api/sessions/{id}
POST   /api/sessions/{id}/connect | disconnect | send
GET    /api/serial/ports             -> COM 列表（含 VID/PID）
POST   /api/sessions/{id}/http       发起一次 HTTP 请求（返回完整响应；大响应走流）
GET    /api/fs?path=                 后端本地文件浏览（上传/下载用）
POST   /api/upload                   流式上传到后端临时区
WS     /ws/session/{id}              双向：{type: data|state|log|progress, dir, ts, enc, payload}
WS     /ws/events                    全局：会话状态、错误、通知
```

- 错误格式：`{code, message, detail, sys_errno}`。
- 鉴权：`X-Auth-Token` 头（静态页与 WS 同 token）。

## 10. 风险与取舍

1. SMB / SSH 自研不现实 → 依赖库；版本与算法兼容是主要坑。
2. 老设备算法与编码兼容 → 需要「兼容模式」开关，且必须有真机验证。
3. LGPL（libsmb2 / libssh）静态链接的合规成本。
4. 前端大日志 / 长列表性能（虚拟滚动 + 批量合并渲染）。
5. Windows 串口驱动差异、端口独占。
6. 防火墙 / 杀软对监听端口的拦截与误报。
7. 范围膨胀（HTTP/2、SMB 服务端等"看起来简单"的东西）→ 用 §4.9 守住边界。
